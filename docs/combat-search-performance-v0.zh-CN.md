# Combat Search Performance V0

## 当前默认路径

当前搜索使用：

```text
isolated prepared entrance packet
→ compact prefix/suffix replay（动作数达到阈值时）
→ 单次实体 Transformer 编码
→ Policy / action-resource / state-value 多头共享编码结果
→ 复用信息键阶段已经构造的模型样本
→ 真实引擎逐动作推进
```

对应配置为：

```json
{
  "engine_restore": {"mode": "cached_batch_auto_prepared"},
  "model_inference": {
    "reuse_entity_encoding": true,
    "reuse_precomputed_sample": true
  },
  "engine_transition_cache": {"enabled": true, "maximum_entries": 10000}
}
```

所有速度测试使用同一个 P1 CUDA checkpoint、相同根状态、相同搜索种子与相同预算。每组配对交错执行顺序，以减少热机和运行顺序偏差。速度数据只表示当前三场代表性战斗，不直接等同于全部战斗的稳定吞吐量。

## 已通过门禁的优化

### Prepared save

入口JSON只解析一次并编码为游戏原生packet；后续 simulation 从packet构造新的 `SerializableRun` 对象图和独立 `RunState`。直接复用解析对象会被游戏加载过程修改，已由地图入口楼层计数回归禁止。

修复后的30次配对restore测试中，packet反序列化相对重新解析JSON的 `load_save` 阶段加速为1.24–1.43x；前缀长度8时完整restore加速为1.04–1.11x。空前缀的完整restore为0.96–1.27x，说明较小状态下收益可能被其他阶段波动抵消。修复前直接复用可变 `SerializableRun` 得到的旧速度数字不再作为有效依据。

### 共享实体编码

旧路径在每个新树节点上重复运行实体 Transformer：动作策略/资源、Combat Tool 状态价值、MCTS 状态价值各一次。新路径只编码一次，再分别运行各输出头。

| 场景 | 128 search | 256 search | 模型推理加速 |
|---|---:|---:|---:|
| Act 1 | 1.26x | 1.06x | 约1.42x |
| Act 2 | 1.29x | 1.10x | 约1.39x |
| Act 3 | 1.15x | 1.09x | 约1.43x |
| 分预算均值 | 1.24x | 1.08x | 1.42x |

跨全部 Act、预算和重复的完整搜索加速均值为1.16x。

所有配对的最终根动作、原始搜索动作、Policy 动作、树节点数和引擎动作数完全一致。

### 复用预计算模型样本

搜索查找信息键时已经将引擎状态转换为模型样本。旧路径在遇到新节点后又转换一次；新路径直接把同一份样本交给节点扩展器。

| 场景 | 128 search | 256 search |
|---|---:|---:|
| Act 1 | 1.16x | 1.00x |
| Act 2 | 1.27x | 1.02x |
| Act 3 | 1.13x | 1.03x |

该优化在树仍快速增长的较低预算下更有效；高预算中大部分 simulation 会访问已有节点，因此收益自然收敛。所有搜索一致性门禁仍通过。

## 256 simulations 阶段剖析

在共享编码和 prepared-save 已启用的单次代表性测量中：

| 场景 | restore | engine actions | model inference | Python/其他 |
|---|---:|---:|---:|---:|
| Act 1 | 22.3% | 45.3% | 8.8% | 23.6% |
| Act 2 | 21.4% | 19.4% | 25.7% | 33.5% |
| Act 3 | 35.7% | 21.2% | 17.7% | 25.4% |

动作推进中，`play_card` 的中位往返约0.54–0.86 ms，`end_turn` 约0.68–1.40 ms；Act 3 的结束回合通常更贵，因为它需要结算敌方行动、抽牌和新回合状态。Act 2 的 `select_cards` 中位约0.60 ms。

这些比例会随树形、卡组和敌人机制变化，不能把单次结果外推为固定常数。它们足以说明：存档解析、重复模型编码和重复样本转换已经不再是唯一瓶颈，后续必须针对真实动作推进与搜索树调度。

## Verified transition path cache

搜索现在可以按“determinization索引 + 从根开始的完整语义动作路径”缓存真实引擎返回状态。缓存不直接代替引擎结算：它只用于提前沿已知树节点选择路径，随后由 `restore_combat` 使用compact suffix一次性重放到路径末端；每次接回引擎时都将重放结果与缓存状态逐字段比较。缓存每个根搜索独立创建，默认最多10000条，搜索结束即释放。

在隔离prepared-save修复之后，Act 1–3、128/256 simulations、每组两次交错配对结果如下：

| 场景 | 128 search | 256 search |
|---|---:|---:|
| Act 1 | 1.20x | 1.12x |
| Act 2 | 1.17x | 1.03x |
| Act 3 | 1.20x | 1.07x |
| 分预算均值 | 1.19x | 1.07x |

跨全部Act、预算和重复的完整搜索加速均值为1.13x。

三场的最终根动作、原始搜索动作、Policy动作、树节点数和逻辑动作数全部一致。256预算下，实际逐动作IPC分别由约1857降至1266、865降至648、739降至309；其余命中路径仍由真实引擎批量重放并验证，而不是由Python近似转移。

在512 simulations的进一步压力测试中，三场搜索仍保持完全一致，完整搜索加速分别为1.38x、1.16x和1.20x，均值1.25x。实际逐动作IPC/逻辑动作分别为2238/3984、1304/1911和657/1663，缓存条目数均低于默认10000条上限，没有跳过插入。对应吞吐量由76.5→105.4、58.6→68.1、48.8→58.5 simulations/s。路径重复随预算增加而上升，因此该优化在512预算下比256预算更有价值。

## 完整栈总账与停止门禁

最终总账没有把各项局部加速相乘，而是在同一批 Act 1–3 根状态、同一 CUDA checkpoint、相同搜索种子与相同预算下直接配对：

- 原始栈：JSON cached-batch restore、重复实体编码、重复模型样本转换、无转移路径缓存；
- 当前栈：隔离 prepared packet、compact replay、共享实体编码、模型样本复用、验证式转移路径缓存。

每组重复两次并交错运行顺序。所有配对的最终动作、搜索动作、Policy动作、树节点数和逻辑引擎动作数完全一致。

| 场景 | 128 | 256 | 512 | 当前512吞吐量 |
|---|---:|---:|---:|---:|
| Act 1 | 1.46x | 1.31x | 1.36x | 126.9 simulations/s |
| Act 2 | 1.43x | 1.34x | 1.33x | 72.4 simulations/s |
| Act 3 | 1.56x | 1.37x | 1.40x | 63.7 simulations/s |
| 分预算均值 | 1.48x | 1.34x | 1.37x | — |

全部预算的配对加速均值为1.40x。128预算受首轮冷启动波动影响较大；更稳定的256/512预算均值为1.35x，即同预算搜索耗时约减少26%。

当前512预算中，单独把模型推理时间理想化为零，整场搜索理论上最多再提升约1.10–1.38x；把每次根状态恢复时间理想化为零，理论上最多约1.31–1.55x，真实实现只会得到其中一部分。叶节点批处理还会改变PUCT访问顺序，最小状态投影需要重新审计特殊机制，而独立C++模拟器属于重新实现游戏规则，并非小规模吞吐优化。

因此当前不存在一个能在保持真实引擎语义和低工程风险的前提下继续获得大幅度加速的单点。速度优化线在此停止；后续优先回到战斗能力、适配器和上层Agent接口。只有未来搜索预算明确成为在线系统的主要阻塞，并且跨更多战斗剖析得到稳定证据时，才重新评估批处理或独立模拟器。
