# Combat Potion Evaluator V0

## 目标与版本边界

本模块为上层资源 Agent 提供逐药水的结构化战术证据，而不是直接让战斗网络用一个不可解释的
标量决定是否消耗药水。当前范围严格锁定：

- 游戏正式版 `v0.107.1`；
- Steam build `23811903`；
- 单人 Ironclad；
- 45 种公共常规药水、3 种 Ironclad 独有药水、3 种公共特殊药水。

本机本地化中还存在一个 `DEPRECATED_POTION`，不属于有效内容。其他角色的12种专属药水也不在
本阶段范围内。当前线上资料出现的 Ambergris 不存在于锁定程序集，因此不能混入 v0.107.1 注册表。

代码注册表位于 `src/sts2_dataset/combat_potions.py`。

## CLI 能力门禁

`tools/audit_combat_potions.py` 为每瓶药水启动独立 sts2-cli 进程，执行：

1. 创建固定 Ironclad A0 战斗；
2. 注入一瓶待测药水；
3. 检查药水 ID 与目标类型；
4. 执行药水动作；
5. 若出现 `card_select`，显式完成一次选择；
6. 检查引擎异常日志和选择契约。

完整审计：

```powershell
& .\.venv\Scripts\python.exe tools/audit_combat_potions.py `
  --output artifacts/combat_potion_cli_audit_v01071.json
```

2026-08-17 的锁定结果：

```text
audited:                    51
active-use execution OK:   50
passive-created:             1  (Fairy in a Bottle)
engine warning/error:        0
selection contract failure: 0
```

显式暴露并完成 `card_select` 的9种药水：攻击、技能、能力、无色、赌徒特酿、灰水、癫狂之触、
预知之滴和液态记忆。液态记忆在弃牌堆只有一个合法目标时会由游戏自动解析；审计场景准备两个目标，
确保选择接口真正被测试。

该门禁仅证明真实引擎可以执行这些药水，不证明药水价值估计正确。

## 评估边界

当前51种药水按首要估值方式分为：

| 评估器 | 数量 | 第一版处理方式 |
|---|---:|---|
| paired_turn_boundary | 9 | 同一动作前缀下比较禁用/允许药水的回合边界 |
| nested_choice | 11 | 先使用药水，再搜索选牌、选子集或下一张触发牌 |
| sampled_rollout | 9 | 多个玩家可见状态一致的 determinization 上估计均值、尾部风险 |
| persistent_rollout | 18 | 至少展开多回合；部分药水需要到战斗结束 |
| upper_resource | 3 | 同时涉及战斗外回血、永久生命、金币或药水库存价值 |
| passive_reserve | 1 | 瓶中精灵只输出保留/触发价值，不生成主动使用动作 |

第一批反事实评估只实现 `paired_turn_boundary`，但仍必须重新优化两条分支的后续出牌，不能只比较
喝药前后的单步数值。格挡药水的主要收益可能不是直接减少承伤，而是替代一张防御牌、释放能量用于
输出。

sts2-cli 当前不能从任意战斗动作状态写出精确存档；现有战斗搜索通过“战斗入口状态 + 已执行动作前缀”
重放到同一根状态。因此药水分支必须沿用同一方式：两条分支共享战斗入口、动作前缀和
determinization，只在根节点改变药水约束。

## 预期输出

药水提案至少分离两类量：

- 战术收益：死亡风险下降、即时/整场生命节省、击杀概率、回合数、能量和卡牌替代价值；
- 估计可靠性：边界是否由引擎精确执行、随机样本数、搜索覆盖率和结果方差。

`tactical_necessity` 不能冒充概率，`estimate_confidence` 也不能代表药水值得使用。上层 Agent 使用
局外路线、药水槽压力和未来敌人信息设置动态资源影子价格，再决定允许、拒绝或延后使用；下层搜索
负责批准后的精确使用时机和动作顺序。

## 第一批实现结果

`paired_turn_boundary` 已实现为真正的同根反事实，而不是把药水的静态数值直接加到评分中：

- `turn_boundary_current_root` 支持强制纳入指定药水的全部合法目标分支；
- 使用分支与保留分支共享战斗入口、动作前缀、可见信息 determinization、搜索预算和价值模型；
- 使用分支强制以目标药水作为根动作，保留分支在整条回合路径中禁用该药水；
- 两条分支都会重新优化后续出牌；
- 下层目标显式设为 `potion_cost=0`，不混入上层的局外资源影子价格；
- 输出 `combat_value_gain`、死亡风险下降、预测战后生命变化以及引擎实测的 HP、伤害、击杀、
  能量和手牌差分；
- `tactical_necessity` 与 `estimate_confidence` 暂时保持 `null`，在多场校准前不冒充概率。

实现位于：

- `src/sts2_dataset/combat_potion_evaluator.py`：配对与收益向量；
- `tools/run_combat_potion_counterfactual.py`：真实 CLI + CUDA 固定场景执行器；
- `tools/run_combat_turn_boundary_eval.py`：指定药水根动作与禁用约束。

9 种第一批药水均已在真实 v0.107.1 CLI 中通过“使用/保留”接口门禁：格挡、能量、爆炸安瓿、
火焰、肌肉、速度、固化、镣铐和药水形状的石头。该门禁使用较低预算，只证明配对搜索可执行，
不把单场数值解释为药水强弱排名。

四个较高预算的方向性检查进一步表明：

| 场景 | 药水 | 引擎实测 | 解释 |
|---|---|---:|---|
| Act 1 Floor 17，敌人首回合不攻击 | 格挡药水 | 省血 `0`，价值 `-0.041` | 无收益时应保留 |
| Act 1 Floor 2，首回合总攻击14 | 格挡药水 | 省血 `3`，价值 `+0.079` | 可替代部分防御但非保命 |
| Terror Eel，44 HP，首回合攻击16 | 格挡药水 | 省血 `6`，价值 `+0.138` | 正常高压但非致死 |
| 同一 Terror Eel 人工降到5 HP | 格挡药水 | 死亡风险下降约 `0.999` | 受控保命场景，非真实验证样本 |
| Terror Eel，44 HP | 火焰药水 | 多造成20伤害，价值 `+0.031` | 正确识别输出收益，尚未形成击杀 |
| Corpse Slugs，动作前缀后目标20 HP | 火焰药水 | 击杀 `+1`、省血 `3`，价值 `-0.231` | 引擎与价值头方向冲突 |

保命测试还发现：`game_over` 死亡状态不再暴露敌人、能量与手牌。精确差分现在逐字段携带
`*_observed` 标记；无法观测的敌人伤害、击杀、能量和手牌差分输出 `null`，不再把字段消失误报成
击杀或资源变化。

精确击杀场景没有被当作“火焰药水不值得使用”的结论。该分支由真实引擎确认击杀一只 Corpse
Slug、当回合多造成20点伤害并节省3点生命，但独立叶节点 Value 将死亡概率从约 `0.005` 估到约
`0.057`。这表明现有 Value 对训练中稀少的“药水击杀 + 敌人特殊状态变化”存在明显失校准。
因此第一版输出必须保留两条证据通道：引擎执行后的精确短期事实与学习模型的远期估计；两者方向
冲突时应降低估计置信度并请求更深展开或怪物机制检查，而不能直接生成高置信度使用/保留结论。

将同一根状态扩大到5个常规根候选、beam 5、最多6个本回合动作、4个 determinization 和4个 CLI
worker 后，冲突仍然存在：引擎确认击杀 `+1`、伤害 `+26`，学习 Value 仍为 `-0.317`，预测死亡风险
仍上升约 `0.054`。因此它不是最初小 beam 的偶然漏搜；但当前叶边界仍停在下一玩家回合，尚不能只凭
这一结果区分“Value 失校准”和“Corpse Slug 死亡触发的更长期代价”。下一门禁应是对冲突分支进行
战斗终局回放或加入可验证机制事实，而不是继续无上限扩大同一回合 beam。

### 战斗终局回放

冲突分支现已支持三种同入口终局干预：

1. `use_now`：强制当前根动作使用目标药水，之后采用相同 P1 + 回合边界搜索；
2. `hold_now`：强制当前根动作不使用药水，并禁止使用或丢弃该药水直到下一玩家回合；
3. `reserve_entire_combat`：强制相同保留根动作，并在整场战斗中禁止使用或丢弃该药水。

三条分支共享战斗入口存档、动作前缀、游戏 Seed、搜索配置和零药水影子价格。不同动作可能改变后续
RNG 消耗，因此它是固定游戏根上的确定性干预，不宣称每个后续随机事件逐项相同。

Fire Potion / Corpse Slugs 受控低血根的真实终局为：

| 分支 | 终局 | 最终生命 | 回合数 | 药水时机 |
|---|---|---:|---:|---|
| 立即击杀低血目标 | 胜利 | 80 | 3 | 第一回合立即使用 |
| 当前回合保留 | 胜利 | 80 | 3 | 第二回合使用 |
| 整场保留 | 胜利 | 74 | 5 | 未使用、未丢弃 |

相同配置完整重复一次后，三条分支的动作序列、胜负、最终生命、回合数和决策数完全一致。因此对这个
固定根可以确认：药水的战斗内价值为相对整场保留节省6 HP和2回合；立即使用与延后一回合在终局上
等价。下一回合 Value 给出的约 `-0.298` 使用收益和约 `+0.052` 死亡风险变化不受真实终局支持。

当前训练快照中共有16,721条可训练战斗动作，其中仅307条使用药水（约1.84%）；Fire Potion 只有
6条，全部位于训练集，验证集与测试集均为0，且没有 Corpse Slug 场景。验证集全部药水动作也只有
22条，P1 的药水动作 Top-1 为 `2/22`。此外当前 Value 的验证 HP-loss MAE 约为0.072个最大生命比例，
在80 HP量级约等于5.8 HP，已经接近本例两分支的真实6 HP差。因此主要问题不是 CLI 模拟不确定，而是
人类 on-policy 数据对罕见药水反事实状态覆盖不足，现有全局 Value 指标也无法保证这类条件分布校准。

## 下一实现门禁

1. 将终局回放作为引擎/Value 冲突、高死亡风险和特殊机制敌人的条件式教师，而不是每个动作都运行；
2. 在更多药水状态上生成固定根成对终局结果，校准 `estimate_confidence`，之后再讨论必要性标量；
3. 将已校准的收益向量作为可选提案接入 `Combat Tool`，仍由上层 Agent 决定资源价格；
4. 实现 `nested_choice` 的显式选择展开；
5. 随机和持续型药水必须单独通过 determinization/长程门禁，不能沿用即时估值结果。
